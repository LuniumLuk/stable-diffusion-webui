1 · What data is saved when an image is generated

1.1 Save pipeline (txt2img / img2img / inpaint)

① create_infotext()modules/processing.py builds the parameters string per image (prompt, negative, params, fork extras).
② PNG info chunkA1111 writes the string into the PNG parameters tEXt chunk.
③ .txt sidecarsave_txt default is True in this fork → same-name .txt beside the image.
④ on_image_saved hookscripts/endorsed_gallery.py::on_image_saved parses infotext → endorsement_db.index_image() row.
⑤ Sync All (backfill)mtime-based rescan of txt2img/img2img sample dirs + outdir_save; grids & removebg excluded.
⑥ Thumbnails192px thumb + 1024px preview webp generated lazily into cache/gallery_thumbs / gallery_previews.
⑦ ActionsEndorse copies the file to outputs/endorsed/YYYY-MM-DD/ and stores the copy path + original path.

3.4 Known gaps observed while auditing

  • Filter parity: the 3 scan views (Composed / Image Maker / None SDXL) ignore the Date dropdown; search covers only the display path, not prompt text (except None SDXL where prompt comes from sidecars but still isn’t searched).
  • Sorting: no sort picker; newest-first only (+ one reverse checkbox).
  • Trash lifecycle: 35,462 rows with no Restore / Purge / Empty-Trash UI; trash rows include metadata but there is no way to purge them (disk impact is only cache rows).
  • Orphaned caption data: 476k dislike-labelled tag rows with 0 dislikes live.
  • Index coverage: removebg outputs are deliberately excluded from the index; nano-banana (4) / comic_maker (161) / sana (0) outputs exist on disk but have no gallery view at all.
  • Two gallery front-ends (desktop Gallery tab + SD Lite “Gallery” screen with 9 views) share DB state but not filter/action code.

4 · Suggested upgrades & “formalize first”

How to read this: “Formalize first” = the design documents/specs to write before touching code, because every later upgrade leans on them. The roadmap below is ordered by dependency and by value-per-effort against the live numbers above.

4.1 Formalize first (spec phase — no code)

#SpecWhy it must come firstContents / acceptance
F1 Unified Gallery Item & Provider model Today there are 4 different data pipelines (paged SQL, SQL+sidecar merge, folder scan, archived-splice) and 3 key schemes. Every inconsistency in §3.4 traces back to this. Without it, each new filter/view/action must be implemented 4×. Define GalleryItem (key, provider, path, mtime, state flags, metadata, caption tags, cache urls) and GalleryProvider (list(filters, sort, page) → items+total; capability map for filters/actions). Register: generated, endorsed, disliked, archived, staged, trash, composed, image_maker, none_sdxl (+ later removebg, nano-banana, comic_maker, sana). Acceptance: a new source = 1 provider, 0 UI changes; all views accept the same filter object.
F2 Filter & Sort Matrix The current control set is fixed and uneven (date ignored by scans; search means different things per view). Users cannot slice 4k+ images by model/sampler/tag; sort is frozen. Define FilterSet {search syntax, date-range, models[], samplers[], caption tags[], states[], resolution/aspect, seed range, has-metadata} + SortSpec {key: date|seed|model|steps|resolution|state, dir}. Per-provider capability flags drive grey-out in UI. Search grammar: quoted phrases, -exclude, tag:name, later FTS5. Acceptance: written per-provider capability table + UI spec for unsupported controls.
F3 Tag taxonomy & storage “Tags” conflates 3 concepts (§2). There is no user tagging, no collections, no tag filter, and orphan cleanup is undefined — that’s why 476k stale dislike rows exist. Split: state (existing 1-per-item tables — keep), caption tags (rename semantics of image_tags, keep scores), user tags/collections (new gallery_tags + item_tags: colour, rename/merge/delete, multi-assign, filterable). Define case folding, limits, bulk tagging, export/import, orphan + retention policy. Acceptance: tag filter in every DB view; caption purge rules documented.
F4 Trash lifecycle & storage policy 35,462 trash rows already, zero restore/purge tooling. Trash currently deletes files + caches immediately (no undo), while keeping metadata forever — that contract must be written down and surfaced. Define: retention (row cap / age), Restore semantics (file copy is gone → what restores?), Purge / Empty-Trash (rows only) vs Delete-now, per-item vs bulk, disk accounting into Statistics. Document the “recycled item_key clears trash row” behavior. Acceptance: UI spec for Trash view buttons + counter; policy table.

A.3 Behavioural quirks to keep in mind

  • Indexing skips grid images and removebg attachments; re-indexing clears a stale trash row for the same item_key.
  • Endorse = copy (original stays); unendorse deletes the copy only. Archive/dislike/stage are DB-only flags.
  • Delete-Archived-and-Disliked moves metadata to trash, deletes originals + cached thumb/preview (cache keys use path+mtime).
  • Thumbnails can outlive originals (archived+deleted case) via the DB-stored mtime fallback.
  • Scan views hide archived (None SDXL → moved into Archived view) and trashed items; item keys for qwen/krea2 are shared with SD Lite.
  • Date filter defaults to 1 day — older images are hidden until you switch to “All time”.
  • Trash guard: any state-changing action on a trashed item is neutralised server-side.
