# LoRA Data Maker (no prompt files)

> **Superseded for character LoRAs.** This sheet-based flow cuts 3x4 / 3x3
> contact sheets into ~580px tiles, which trains blurry at SDXL sizes and
> needs a manual delete pass. Use
> [README_lora_dataset_builder.md](README_lora_dataset_builder.md)
> (`lora_dataset_builder.bat`) instead: one full-resolution image per call, a
> fixed shot plan, automatic verification and plan-accurate captions.

`lora_data_maker.bat` + `gemini_workflow/lora_data_maker.py`. Prompts are
curated and built in — the only inputs are your pictures.

## Usage

```bat
.\lora_data_maker.bat --avatar .\tmp\img_chara_rana.png
```

| input | what it makes (with the default `avatar_tasks`) |
|-------|---------------|
| avatar A | one 3x4 face grid -> **12 different expression images** |
| `--fullbody B ...` | *(dormant)* outfit sheets are off by default — see below |

Only the avatar → portrait grids are generated by default. Outfit
(upper / fullbody) sheets are **disabled**: `outfit_tasks` ships as an empty
list, so `--fullbody` pictures are accepted but ignored (the run prints a
note). To re-enable them, add `outfit_tasks` entries to the YAML config — then
the earlier behaviour returns: each fullbody picture adds one upper grid (12)
plus one fullbody grid (12) = 24 images.

Add extra `avatar_tasks` entries (e.g. a 3x3 face grid) to get more portrait
images per run; counts always follow your config.

Repeat the whole plan N times with `--num N` (alias `--variations N`):

```bat
.\lora_data_maker.bat --avatar .\tmp\img_chara_rana.png --num 3
```

With the default config that is 3 × (12 + 9) = **63 images**: each scheme is
generated three times, and every repeat samples new panels/styles, so you get
genuinely different expressions instead of duplicates. `--seed N` still makes
the whole run reproducible.

## Variety (no two sheets are prompted alike)

Each generated sheet samples from built-in pools, so every outfit (and every
`--num` repeat) gets a different prompt:

| element | pool |
|---------|------|
| art style (**per panel**, 12 distinct per sheet) | anime screencap / anime movie / retro 90s anime / light novel / watercolor / vibrant flat / **detailed hatching** / **plain flat colors** / **vibrant saturated colors** / **monochrome grayscale** / pastel / cute simplified / shoujo manga / shonen action / Makoto Shinkai / Akira Toriyama / Naoko Takeuchi / Yoshitaka Amano / Vanripper / Kantoku |
| scene / background | **pure white (#FFFFFF) by default**; when `randomize_panel_scene: true`, per panel from: sunny park / city street / cozy cafe / school classroom / cherry blossom road / rainy street / winter snow / traditional Japanese room / ... (19 scenes) |
| lighting (random per sheet) | soft studio / gentle diffused / bright even / soft top-down |
| panels (12 sampled from 18, random order) | face: 18 expressions; upper & fullbody: 18 poses each |

When `--main-style` is given, `main style` joins the per-panel style draws for
the requested share of panels (see below) instead of only the config styles.

## Main style reference (`--main-style`)

Sometimes the look you want only exists in a picture that is *not* your
character — typically a multi-character illustration where you like the
rendering but none of the people.

```bat
.\lora_data_maker.bat --avatar .\tmp\img_chara_rana.png ^
  --main-style .\tmp\style_ref_a.png .\tmp\style_ref_b.png ^
  --main-style-perc 75
```

- `--main-style IMG [IMG ...]` attaches those images as **ART STYLE ONLY**.
  The prompt labels them `MAIN STYLE reference image(s)`, states that they are
  separate illustrations which usually contain several different characters,
  and forbids copying their characters, faces, hairstyles, eye colors,
  outfits, poses or composition — every panel still shows exactly the one
  character defined by the `--avatar` reference. Hard
  negatives (`NO extra characters`, `NO copying faces, outfits or poses from
  the MAIN STYLE reference`, `NO multi-character panels`) back it up.
- `--main-style-perc N` (0-100, default **75**) is the share of *panels* that
  follow the main style, picked at random positions inside each sheet. The
  remaining panels keep the `--style` pin or the per-panel random styles, so
  the LoRA still learns style variation instead of overfitting one look. A
  3x4 sheet at 75% gives 9 main-style + 3 random panels, a 3x3 sheet 7 + 2.
  `0` disables the feature (the images are then not attached at all).
- The style images are appended **after** the character references and every
  reference is addressed by role and file name in the prompt, so a style
  picture can never be mistaken for the face or the outfit.
- With `--captions`, main-style panels carry the `main style` tag, so you can
  separate them from the random-style panels during training.

## Custom requirements (`--desc`)

When the built-in pools are not enough, add your own instructions — a clothing
detail, an expression rule, a prop, or a background you want instead of the
pure white default:

```bat
.\lora_data_maker.bat --avatar .\tmp\img_chara_rana.png ^
  --desc "she wears a navy sailor uniform" ^
  --desc "keep her red hair ribbon on the left side"
```

- Each `--desc` (or each line of a multi-line value) becomes a bullet in a
  `USER REQUIREMENTS` section placed right after the sheet geometry, above
  every other instruction, with the wording *"highest priority for this whole
  sheet … follow them strictly"*.
- Repeat the flag for several points, or put a literal `\n` between them on one
  line: `--desc "she wears a navy sailor uniform\nkeep her ribbon on the left"`.
  Do **not** paste a real newline into a `.bat` command line — cmd splits the
  line there and the flags after it (including `--dry-run`) are lost.
- Precedence is explicit: user requirements win over the default art-style and
  background wording, but **never** over the grid layout, the
  exactly-one-character rule, or the identity taken from the reference images —
  so a `--desc` cannot silently break the dataset structure.
- Because a description may legitimately describe a scene, passing `--desc`
  relaxes the hard white-background negatives: instead of "no scenery, no
  props, no floor, no horizon", the prompt says the background stays pure white
  *unless the user requirements describe a background*. Without `--desc` the
  strict pure-white rule is unchanged.
- The text is stored in the dry-run JSON (`"desc"`) and the run manifest, so a
  dataset can be reproduced exactly.

## YAML config

`config_states/lora_data_maker.yaml` (created automatically on the first run,
or point anywhere with `--config PATH`) controls everything random about
styles and scenes:

```yaml
randomize_panel_style: true    # true  -> each panel gets its own random style
                               # false -> one uniform style (first list entry)
styles:                        # the FULL art-style list (tag + text)
  - tag: detailed hatching
    text: "detailed ink hatching style, fine cross-hatched pen shading, bold outlines"
  ...

randomize_panel_scene: false   # true  -> each panel gets its own random scene
                               # false -> PURE WHITE (#FFFFFF) background in
                               #          every panel (the default)
scenes:                        # the FULL background-scene list (tag + text)
                               # dormant while randomize_panel_scene is false
  - tag: plain white background
    text: "background: plain solid white background, no props"
    weight: 8                  # optional weight (default 1) - a raised weight
                               # here keeps most panels clean white
  ...

# Sheet schemes: what grids get generated, in what aspect/size.
avatar_tasks:                  # run for the avatar picture(s)
  - grid: [3, 4]               # cols, rows
    aspect: "3:4"
    size: "2K"
  # - grid: [3, 3]             # example: also render a 3x3 face grid
  #   aspect: "2:3"
  #   size: "2K"

outfit_tasks: []               # EMPTY by default -> avatar/portrait grids
                               # only, and --fullbody is ignored.
                               # Add entries to re-enable outfit sheets:
                               #   - kind: upper          # upper-body grid
                               #     grid: [3, 4]
                               #     aspect: "3:4"
                               #     size: "2K"
                               #   - kind: fullbody       # full-body grid
                               #     grid: [3, 4]
                               #     aspect: "3:4"
                               #     size: "2K"
```

- **Every style and scene entry may carry a `weight`** (default 1): weighted
  random sampling makes heavier entries appear more often across panels while
  keeping panels distinct within a sheet. `plain white background` ships with
  a raised weight so scene randomization does not drown your sheets in props.
- `avatar_tasks` / `outfit_tasks` are plain lists: add entries to generate
  additional grids (e.g. a 3x3 face grid), each with its own grid, aspect
  ratio and image size; one sheet is generated per list entry per picture.
  `outfit_tasks` is empty by default, so only the avatar/portrait sheets run.
- Both randomization toggles can be on at once: every panel then carries its
  own art style *and* its own background scene.
- `--style TAG` on the command line always wins over `randomize_panel_style`;
  `--aspect-ratio` / `--image-size` override every task.
- `--seed N` makes a run reproducible; PyYAML is preferred, but a built-in
  YAML-subset loader keeps the file format working if it is not installed.

- Each panel of a sheet declares its own art style inside its description
  ("Panel art style: ..."), so one image already yields 12 style variants of
  the same character/outfit — while the sheet-framing wording stays in the
  concise mode that keeps the grid layout accurate.
- `--style TAG` pins one art style for all 12 panels (e.g.
  `--style "monochrome grayscale"`).
- `--seed N` makes the whole run reproducible (same style/lighting/panel draws).
- If a sheet fails (for example an artist style is refused), the pipeline
  resamples styles/panels and retries automatically.
- With `--captions`, each caption carries its panel's style tag
  (`rana, 1girl, solo, upper body, front view, arms crossed, detailed hatching`),
  so training can separate character from style; main-style panels carry the
  `main style` tag instead.
- The artist-style entries can occasionally be blocked by the image model;
  remove any line from `STYLES` in `gemini_workflow/lora_data_maker.py` if
  one keeps failing.

## Grid compliance

The sheet-framing wording stays in the concise mode that produced the most
accurate grids: "clean 3-column by 4-row matrix of 12 separate square panels
... wide uniform white gutters", one panel line per cell (`R{r}C{c}`), and
light negative reminders (no merged / missing / extra panels, no uneven
rows, no crooked grid). Art-style variety is expressed compactly inside each
panel line ("Panel art style: ...") so it does not bloat the framing text.
If a sheet still comes back misaligned occasionally, re-roll it
(`--num 2`) and keep the good sheet, or raise `--grid-padding`.

## Output

```
training_data/lora_<trigger>/     <- trigger inferred from img_chara_<name>.png
  <trigger>_face_001.png ... <trigger>_face_012.png      (12 expressions)
  <trigger>_face_013.png ...                             (extra avatar_tasks)
  <trigger>_o01_upper_001.png ...                        (only when
  <trigger>_o01_fullbody_001.png ...                      outfit_tasks is
  ...                                                     configured)
```

Every output image is named with the trigger as prefix (e.g.
`rana_face_001.png`, `rana_o01_upper_007.png`), so files from different
characters never collide even if you merge dataset folders. Just a flat
folder of images. Add `--captions` to also write kohya-style
`.txt` tag files beside each image (trigger + 1girl + solo + panel tags).
Raw sheets/tiles/manifest stay in `outputs/lora_data_maker/<timestamp>/`.

## Flags

| flag | default | meaning |
|------|---------|---------|
| `--avatar A [A2 ...]` | required | avatar picture(s) = identity refs |
| `--fullbody B C D ...` | none | outfit pictures; only used when `outfit_tasks` is configured (empty by default) |
| `--out DIR` | `training_data/lora_<trigger>/` | result folder |
| `--num N` | 1 | number of variations: run the whole plan N times (each sheet = cols x rows images). `--variations N` is an alias |
| `--style TAG` | per config | pin one art style for every panel (see YAML config) |
| `--main-style IMG ...` | none | art-style reference image(s), usually multi-character illustrations; their characters are never copied |
| `--main-style-perc N` | 75 | % of panels that follow the main-style reference (0 disables it) |
| `--desc TEXT` | none | custom requirement/supplement injected as a high-priority `USER REQUIREMENTS` section into every sheet prompt (repeatable / multi-line) |
| `--config PATH` | `config_states/lora_data_maker.yaml` | YAML config file |
| `--seed N` | random | reproducible style/scene/panel sampling |
| `--grid-padding P` | 8 | trim P px from each cell border |
| `--image-size 1K\|2K\|4K` | per task | override image size for every scheme |
| `--aspect-ratio W:H` | per task | override aspect ratio for every scheme |
| `--captions` | off | write `.txt` tag files beside images |
| `--trigger WORD` | inferred | folder name + captions |
| `--dry-run` | - | print plan only, no API calls |
| `--selftest` | - | offline split/parse check |
| `--retries N` / `--image-model` / `--api-key` / `--output-dir` | legacy | API behavior |

## Tips

- Run `--dry-run` first to see the exact plan, sampled styles and counts.
- `--selftest` verifies the split/caption/prompt-assembly machinery without the API.
- The built-in face pool covers 18 expressions, upper/fullbody pools 18 poses
  each; every sheet samples 12 of them in random order.
- The older prompt-file pipeline still lives at `image_maker.bat`.
